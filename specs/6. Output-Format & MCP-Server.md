# **Output-Format & MCP-Server Integration**

Dieses Dokument definiert, in welcher Struktur die von den LLMs (Stufe 3/4) extrahierten Regeln gespeichert werden und wie der MCP-Server diese an Coding-Agenten ausliefert.

## **1\. Das Rule-JSON-Schema (Datenmodell)**

Jede extrahierte Regel (egal ob aus Stufe 3 oder 4\) *muss* diesem JSON-Schema folgen. Dies erzwingt Actionability (Handlungsfähigkeit) für den Agenten.

{  
  "rule\_id": "uuid-v4",  
  "source": {  
    "repository": "org/repo",  
    "pr\_number": 1234,  
    "commit\_hash": "a1b2c3d"  
  },  
  "metadata": {  
    "status": "active", // active, superseded, archived  
    "labels": \["action:accepted\_modified", "reason:explanation", "topic:architecture\_design"\],  
    "confidence\_score": 0.95  
  },  
  "scoping": {  
    "language": \["typescript", "javascript"\],  
    "path\_patterns": \["/src/modules/payments/\*\*", "\!/src/\*\*/\*.test.ts"\] // Wo gilt die Regel?  
  },  
  "content": {  
    "title": "Use Composition over Inheritance in Payment Module",  
    "description": "To maintain flexibility with different payment providers, avoid deep inheritance trees.",  
    "condition": "When creating a new PaymentProvider or extending an existing one.",  
    "enforcement\_prompt": "Always use interface composition. Do not extend base classes. Inject dependencies via constructor.",  
    "examples": {  
      "bad": "class StripeProvider extends BaseProvider { ... }",  
      "good": "class StripeProvider implements PaymentStrategy { constructor(private api: StripeApi) {} }"  
    }  
  },  
  "migration\_context": { // Optional: Nur gesetzt, wenn reason:migration\_instruction zutrifft  
    "is\_migrating": false,  
    "replaced\_by\_path": null  
  }  
}

## **2\. Der MCP-Server (Die Schnittstelle zum Agenten)**

Der MCP-Server (Teil des Headless API-Backends) fungiert als Brücke zwischen der Graph/Vektor-DB und dem Coding-Agenten (z.B. Cursor).

### **Funktionsweise:**

1. **Context Request:** Der Agent sendet seinen aktuellen Arbeitskontext an den MCP-Server (z.B. *„Ich bearbeite gerade src/modules/payments/StripeHandler.ts“*).  
2. **Scoping Match:** Der MCP-Server filtert die DB programmatisch nach scoping.path\_patterns und metadata.status \== active.  
3. **Semantic Match (Optional):** Bei sehr vielen Regeln im gleichen Scope nutzt der Server LightRAG, um nur die Regeln auszuwählen, die semantisch zum aktuellen Task des Agenten passen.  
4. **Injection:** Der Server formatiert die relevanten enforcement\_prompts und liefert sie als System-Prompt-Erweiterung an den Agenten zurück.

## **3\. Human-in-the-Loop & Feedback (Agent zu Pipeline)**

Der MCP-Server ist keine Einbahnstraße. Wenn ein Entwickler im Chat mit dem Agenten sagt: *„Diese Regel ist veraltet, wir nutzen jetzt wieder Vererbung“*, muss das System reagieren.

* **Feedback-Route:** Der Agent nutzt ein MCP-Tool (report\_rule\_feedback), um die rule\_id und die Begründung an den Server zurückzusenden.  
* **Aktion:** Die Regel erhält in der DB das Flag needs\_review. Dies triggert asynchron Stufe 4 (Large LLM), um den neuen Konflikt zu bewerten (siehe Konfliktmanagement), oder zeigt ihn in der Next.js UI zur manuellen Prüfung an.
