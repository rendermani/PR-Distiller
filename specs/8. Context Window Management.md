# **Context Window Management (Token-Limit Strategie)**

Bei großen Pull Requests oder massiven Refactorings droht das Limit des Context Windows (Token-Limit) des lokalen LLMs überschritten zu werden. Dies führt zu Halluzinationen oder "Out of Memory" (OOM) Fehlern auf der GPU.

## **1\. AST-basiertes Code-Slicing (Fokus statt Masse)**

Anstatt dem LLM bei einem PR-Kommentar die gesamte Datei (z. B. 2.000 Zeilen) als Kontext mitzugeben, wird der Code programmatisch "zerschnitten".

* **Die Technik:** Nutzung des Abstract Syntax Trees (AST).  
* **Das Vorgehen:** Bezieht sich ein Kommentar auf Zeile 450, ermittelt das System die umgebende Funktion oder Klasse (z.B. Zeile 400 bis 480).  
* **Der Prompt-Input:** Das LLM erhält *nur* diesen AST-Knoten plus einen Header mit Datei-Imports.  
* **Ersparnis:** Reduziert den Code-Kontext pro Kommentar von potenziell 10.000+ Token auf 200–500 Token.

## **2\. Thread-Pruning (Diskussions-Kompression)**

GitHub-Diskussionen enthalten oft Ping-Pong-Nachrichten ("Geht das so?", "Nein", "Wie wäre es hiermit?", "Ja, besser, aber passe X an").

* **Die Heuristik:** Das System komprimiert lange Threads, bevor sie an Stufe 3/4 gehen.  
* **Der Fokus:** Extrahiert wird primär der *Root-Kommentar* (das ursprüngliche Problem) und die *letzten 2-3 Kommentare* vor dem "Resolved"-Status (die finale Lösung). Der Weg dazwischen wird programmatisch als Rauschen entfernt, es sei denn, Stufe 4 fordert explizit den Volltext an (Deep Dive).

## **3\. Map-Reduce Ansatz für "Mega-PRs" (Stufe 4\)**

Wenn ein ganzer PR analysiert werden muss (z.B. um Architektur-Entscheidungen zu verstehen), wird das Prinzip "Map-Reduce" angewendet:

* **Map-Phase:** Der PR wird in seine logischen Commits oder Dateien aufgeteilt. Das Small LLM (Stufe 3\) analysiert jeden Teil einzeln und erstellt eine Mini-Zusammenfassung (z.B. "In Datei A wurde das DB-Schema geändert").  
* **Reduce-Phase:** Das Large LLM (Stufe 4\) erhält *nicht* den gesamten Code des PRs, sondern nur die Mini-Zusammenfassungen aus der Map-Phase, um die übergeordnete Regel abzuleiten.

## **4\. RAG-Kontext Begrenzung (MCP-Server)**

Wenn der MCP-Server Regeln an den Entwickler-Agenten schickt, darf auch dieser Prompt nicht überlaufen.

* **Top-K Filtering:** Es werden maximal die K=5 relevantesten Regeln pro aufgerufener Datei/Funktion in den Agenten-Prompt injiziert, sortiert nach semantischer Nähe (LightRAG) und Relevanz-Score.
