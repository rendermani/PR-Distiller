# LLM Providers

PR-Distiller uses [litellm](https://docs.litellm.ai/) as its LLM abstraction layer. This means
any provider litellm supports can be used by setting `LLM_API_BASE`, `LLM_MODEL`, and
`LLM_API_KEY` — either as environment variables or through the web UI Settings panel.

The model identifier in `LLM_MODEL` follows the litellm convention:
`<provider-prefix>/<model-name>`. The prefix selects the adapter; the rest identifies the
specific model on that provider.

---

## Ollama (Default)

Ollama runs locally and requires no API key. It is the default configuration for local and
Docker Compose deployments.

**1. Install Ollama**

```bash
curl -fsSL https://ollama.com/install.sh | sh
```

**2. Pull a model**

```bash
ollama pull qwen2.5-coder:7b-instruct
```

The `7b-instruct` variant runs on consumer hardware (8–16 GB VRAM or CPU). For higher quality
use `14b-instruct` if you have sufficient VRAM.

**3. Environment configuration**

```env
LLM_PROVIDER=ollama
LLM_API_BASE=http://localhost:11434/v1
LLM_API_KEY=
LLM_MODEL=ollama/qwen2.5-coder:7b-instruct
```

In Docker Compose deployments the backend reaches Ollama at `http://ollama:11434/v1` because
both containers share a Docker network. The `docker-compose.yml` sets this automatically.

## vLLM (Self-hosted)

vLLM provides an OpenAI-compatible API and is suitable for serving larger quantized models on
a dedicated GPU machine.

**1. Start vLLM**

```bash
python -m vllm.entrypoints.openai.api_server \
  --model Qwen/Qwen2.5-Coder-7B-Instruct \
  --port 8080
```

**2. Environment configuration**

```env
LLM_PROVIDER=local
LLM_API_BASE=http://your-gpu-host:8080/v1
LLM_API_KEY=dummy-key
LLM_MODEL=openai/Qwen/Qwen2.5-Coder-7B-Instruct
```

The `openai/` prefix in `LLM_MODEL` instructs litellm to use the OpenAI-compatible adapter
pointed at `LLM_API_BASE`. The `LLM_API_KEY` value is required by litellm even when vLLM does
not enforce authentication — any non-empty string works.

## OpenAI

```env
LLM_PROVIDER=openai
LLM_API_BASE=https://api.openai.com/v1
LLM_API_KEY=sk-...
LLM_MODEL=openai/gpt-4o
```

Other supported OpenAI models: `openai/gpt-4-turbo`, `openai/gpt-4o-mini`, `openai/gpt-3.5-turbo`.

---

## Anthropic

```env
LLM_PROVIDER=anthropic
LLM_API_BASE=https://api.anthropic.com
LLM_API_KEY=sk-ant-...
LLM_MODEL=anthropic/claude-3-5-sonnet
```

Other supported Anthropic models: `anthropic/claude-3-haiku`, `anthropic/claude-3-opus`.

Note: litellm handles Anthropic's native API format; do not use an `openai/` prefix for
Anthropic models.

---

## Google (Gemini)

```env
LLM_PROVIDER=google
LLM_API_KEY=AIza...
LLM_MODEL=gemini/gemini-2.5-flash
```

`LLM_API_BASE` is not needed for Gemini — litellm routes directly to Google's API using the
`gemini/` prefix. Other supported models: `gemini/gemini-2.5-pro`.

---

## OpenRouter

OpenRouter provides a single API endpoint that proxies dozens of providers. Useful for
accessing high-parameter models without managing separate API accounts.

```env
LLM_PROVIDER=openrouter
LLM_API_BASE=https://openrouter.ai/api/v1
LLM_API_KEY=sk-or-...
LLM_MODEL=openrouter/anthropic/claude-3-opus
```

Other OpenRouter model identifiers: `openrouter/auto`, `openrouter/meta-llama/llama-4-70b-instruct`,
`openrouter/qwen/qwen-3.5-72b-instruct`. The full list is at
[openrouter.ai/models](https://openrouter.ai/models).

## Embedding Models

Embeddings are generated by a SentenceTransformer model running locally in the backend
process. They are used for:
- Storing rule vectors in ChromaDB.
- Querying the most relevant rules for a given code diff.
- Cosine-distance comparison during semantic deduplication.

### Configuration

```env
EMBEDDING_MODEL=BAAI/bge-base-en-v1.5
```

The model is downloaded from HuggingFace on first run and cached locally by the
`sentence-transformers` library. When `EMBEDDING_MODEL` is unset, the system falls back to
ChromaDB's built-in `all-MiniLM-L6-v2` for backward compatibility with existing vector stores.

### Compatible Models

| Model                     | Dimension | Notes                                              |
|---------------------------|-----------|----------------------------------------------------|
| `BAAI/bge-base-en-v1.5`   | 768       | Default. Good balance of quality and speed.        |
| `BAAI/bge-large-en-v1.5`  | 1024      | Higher quality; ~2x memory and compute.            |
| `BAAI/bge-small-en-v1.5`  | 384       | Fastest; adequate for short rule documents.        |
| `all-MiniLM-L6-v2`        | 384       | ChromaDB built-in fallback. Lowest quality.        |
| `nomic-ai/nomic-embed-text-v1` | 768  | Strong general-purpose alternative.               |

### Switching Models (Reindex Required)

Changing `EMBEDDING_MODEL` after rules have been stored will cause dimension mismatches between
old vectors and the new embedding space. After changing the model you must re-embed all stored
rules:

```bash
curl -X POST http://localhost:8923/api/admin/reindex
```

This deletes all existing vectors and re-adds them using the current embedding model. The
operation is safe to run on a live instance — rules are not lost, only re-embedded. See
[api-reference.md](./api-reference.md) for endpoint details.
